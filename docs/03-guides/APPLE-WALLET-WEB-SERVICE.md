## 1. Scope

Source file: `backend/apps/customers/pass_engine/apple_pass_web_service.py`.

Mount: `backend/loyallia/urls.py` builds a separate `NinjaAPI` instance with `auth=None` and `docs_url=None`, adds this router, and mounts it at `path("wallet/apple/", apple_wallet_api.urls)`.

The production URL prefix is `https://rewards.loyallia.com/wallet/apple/`. That value is written into every `pass.json` as `webServiceURL` from `settings.PASS_WEB_SERVICE_URL`, falling back to `PlatformSetting.get("wallet_web_service_url")`. See `backend/apps/customers/pass_engine/apple_pass.py`.

Apple calls these endpoints when a user adds or removes a pass from Wallet, and when a device checks for updates after an empty APNs background push.

## 2. Authentication

Apple sends:

```
Authorization: ApplePass <authenticationToken>
```

`authenticationToken` is the value Loyallia wrote into `pass.json`. Two values are accepted, compared with `hmac.compare_digest`:

1. `pass_data["apple_auth_token"]` — a `secrets.token_urlsafe(32)` value generated by `_ensure_apple_auth_token()` and stored on the pass.
2. Legacy form — `str(customer_pass.id).replace("-", "")`. Older `.pkpass` files were issued with the UUID-no-dashes token. Those wallets must keep refreshing after a random token is stored.

`_apple_token_matches(provided_token, customer_pass)` implements the dual acceptance. Both candidates must be non-empty before comparison.

`_validate_apple_auth()` is used by register, unregister, and download. It requires the `ApplePass ` prefix and a serial that resolves to a `CustomerPass`.

## 3. Endpoint Table

All paths below are relative to `/wallet/apple/`.

| # | Method | Path | Auth | Purpose |
|---|--------|------|------|---------|
| 1 | POST | `/v1/devices/{device_library_id}/registrations/{pass_type_id}/{serial_number}` | ApplePass | Register device, store `pushToken` |
| 2 | DELETE | `/v1/devices/{device_library_id}/registrations/{pass_type_id}/{serial_number}` | ApplePass | Unregister device |
| 3 | GET | `/v1/devices/{device_library_id}/registrations/{pass_type_id}` | optional ApplePass | List passes updated since a tag |
| 4 | GET | `/v1/passes/{pass_type_id}/{serial_number}` | ApplePass | Download regenerated `.pkpass` |
| 5 | POST | `/v1/log` | none | Receive device sync error logs |

`{serial_number}` is the `CustomerPass` primary key (UUID). `{pass_type_id}` must equal `settings.APPLE_PASS_TYPE_IDENTIFIER`.

## 4. Response Contract

### 4.1 Register device (POST)

Request body: `{"pushToken": "<hex string>"}`.

| Code | Condition |
|------|-----------|
| 201 | New `ApplePassRegistration` created |
| 200 | Registration already existed; `push_token` updated |
| 400 | Invalid JSON body, or missing `pushToken` |
| 401 | Wrong or missing `ApplePass` token |
| 404 | Unknown serial, or `pass_type_id` mismatch |
| 410 | Pass exists but `is_active` is false |

`ApplePassRegistration.objects.update_or_create()` keys on `(device_library_id, customer_pass)`.

### 4.2 Unregister device (DELETE)

| Code | Condition |
|------|-----------|
| 200 | Registration deleted, or called when none existed |
| 401 | Wrong `ApplePass` token, or the device is not registered for this pass |

`_require_device_registered()` gates the delete. An unregistered device gets 401, not 200.

### 4.3 List updated passes (GET)

Query parameter: `?passesUpdatedSince=<tag>` (optional).

**Response contract — three outcomes only:**

| Code | Body | Condition |
|------|------|-----------|
| 200 | `{"serialNumbers": [...], "lastUpdatedTag": "<tag>"}` | At least one active pass changed since the tag |
| 204 | empty | Nothing to report: unknown device, unknown pass type, empty result set, or every pass already reported |
| 401 | empty | `ApplePass` header present but token wrong for every registration of this device |

**There is no 404 on this endpoint.** Apple's PassKit Web Service defines exactly the three responses above. Returning 404 makes iOS stop polling, and installed passes then silently stop refreshing. Every "nothing to report" path answers 204. The code comment in `list_updated_passes` marks each of these paths `CONTRACT: 204, not 404`.

Some iOS pollers omit the `Authorization` header on this endpoint. Those requests are still gated by device registration. When the header is present and wrong, the response is 401.

### 4.4 Download updated pass (GET)

| Code | Condition |
|------|-----------|
| 200 | `.pkpass` bytes, `Content-Type: application/vnd.apple.pkpass` |
| 401 | Wrong `ApplePass` token |
| 404 | Unknown serial or pass-type mismatch |
| 410 | Pass inactive |
| 500 | `generate_pkpass()` returned `None` |

The 200 response carries `Content-Disposition: attachment; filename="pass-<serial>.pkpass"` and `Last-Modified` from `customer_pass.last_updated` so Apple can use `If-Modified-Since`. If the pass had no `apple_pass_id`, it is set to the serial and saved.

### 4.5 Device logs (POST `/v1/log`)

Body: `{"logs": ["...", "..."]}` per the PassKit reference. Up to 50 entries, each truncated to 500 characters, are logged at `warning`. Always returns 200.

## 5. `lastUpdatedTag`

The 200 body uses the key **`lastUpdatedTag`**, not `lastUpdated`. Apple reads `lastUpdatedTag` and echoes it back as `?passesUpdatedSince=`. The older `lastUpdated` key was ignored by iOS, so every poll looked like a cold start.

Tag format: UTC ISO 8601 with a `Z` suffix.

```python
last_updated_tag = (
    latest_update.astimezone(UTC).isoformat().replace("+00:00", "Z")
)
```

`+00:00` is not URL-safe. A client echoing it back unencoded gets `+` turned into a space by form decoding, and the tag then fails a strict parse.

### 5.1 `_parse_since_tag(raw)`

Tolerates the URL transport mangling. `request.GET` decodes `+` as a space, so a tag emitted as `2026-09-30T13:00:00+00:00` can arrive as `2026-09-30T13:00:00 00:00`. The parser tries:

1. `raw` as-is (handles the `Z` form and a literal `+HH:MM` form).
2. `raw.replace(" ", "+")` (handles the space-mangled variant).

Returns `None` when neither parses. A failed parse makes the filter pass every active registration, which is the safe cold-start behaviour.

Filtering rule inside `list_updated_passes`: a registration is included when `cp.last_updated > since_dt`. Registrations with `is_active=False` are always excluded.

## 6. Pass Type Gate

`_get_customer_pass(pass_type_id, serial_number)` returns `None` when:

- `settings.APPLE_PASS_TYPE_IDENTIFIER` is empty or unset.
- `pass_type_id` does not equal the configured identifier.

On the list-updated endpoint these conditions answer 204. On register and download they answer 404.

## 7. Registration Storage

Table: `ApplePassRegistration` in `backend/apps/customers/models.py`.

| Column | Meaning |
|--------|---------|
| `device_library_id` | Apple device identifier from the URL |
| `customer_pass` | FK to `CustomerPass` |
| `push_token` | APNs token from the register body |

Unique key: `(device_library_id, customer_pass)`. The push token is what `apple_push.py` `send_pass_update_push()` uses to deliver the empty `{}` background push described in `LOYALLIA-GUIDE-NOTIFY-001`.

## 8. Security Notes

- This router is mounted with `auth=None`. Auth is enforced per endpoint through the `ApplePass` header.
- Token comparison uses `hmac.compare_digest`, not `==`.
- Device identifiers are logged with a `[-8:]` suffix only. Full push tokens and auth tokens are never logged.
- The `.pkpass` generation path loads certificates from Vault through `common.vault.get_secret()`. No secret is written to disk.
