## 1. VAULT CONFIGURATION (deploy/vault.hcl)

### 1.1 Storage Backend
**File:** Line 4-6
```hcl
storage "file" {
  path = "/vault/file"
}
```
**Finding:** Uses `file` storage backend. This is acceptable for single-node development but **not recommended for production HA deployments**. No integrated Raft, no HA auto-failover.

**Recommendation:** For production HA, migrate to `raft` integrated storage or use a Consul backend:
```hcl
storage "raft" {
  path    = "/vault/raft"
  node_id = "node1"
}
```
**Severity:** INFO

### 1.2 TLS Configuration
**File:** Lines 8-16
```hcl
listener "tcp" {
  address         = "0.0.0.0:8200"
  tls_disable     = 0
  tls_cert_file   = "/vault/certs/vault.crt"
  tls_key_file    = "/vault/certs/vault.key"
  tls_min_version = "tls12"
}
```
**Finding:** TLS is properly enabled with minimum TLS 1.2. Self-signed certs are auto-generated by init.sh (line 101-107). However, the init.sh generates a **2048-bit RSA key**:
```hcl
openssl req -x509 -nodes -days 365 -newkey rsa:2048 ...
```

**Issues:**
- RSA 2048 is acceptable but RSA 4096 or ECDSA P-256 is recommended
- Certificate validity is only 365 days - should be 825+ days for production
- Self-signed certs will cause verification failures in Python urllib (see vault.py warning below)

**Severity:** LOW

### 1.3 mlock

**Finding:** mlock is enabled (default). IPC_LOCK capability is correctly granted in docker-compose.yml (line 752).
**Severity:** NONE -- GOOD

### 1.4 UI Enabled

**Finding:** Vault UI is enabled. In production, the UI should only be accessible via a management network or disabled entirely if not needed.
**Severity:** LOW

## 2. VAULT INITIALIZATION (deploy/vault/init.sh)

### 2.1 [CRITICAL] Single Unseal Key = No Key Splitting
**File:** Line 159
```sh
vault operator init -key-shares=1 -key-threshold=1 -format=json >/vault/file/init.json
```
**Finding:** Uses single key share with threshold of 1. This means **there is no Shamir's Secret Sharing protection**. One compromised key = full Vault compromise. There is no quorum protection.

**Recommendation:** Use at least 3-5 key shares with a threshold of 2-3:
```sh
vault operator init -key-shares=5 -key-threshold=3 -format=json >/vault/file/init.json
```
**Severity:** CRITICAL

### 2.2 [WARNING] Unseal Keys Stored Unencrypted on Filesystem
**File:** Lines 159-161, 124-126
```sh
vault operator init ... >/vault/file/init.json
UNSEAL_KEY="$(awk -F '"' '/unseal_keys_b64/ {getline; print $2}' /vault/file/init.json)"
ROOT_TOKEN="$(awk -F '"' '/root_token/ {print $4}' /vault/file/init.json)"
```
**Finding:** Both unseal keys and root token are stored **unencrypted** in `/vault/file/init.json` (same directory as Vault data). This is the equivalent of storing safe combination inside the safe. The file is in the `vault_data` Docker volume.

**Recommendation:** Store init.json encrypted with age/PGP or in a separate encrypted volume. Auto-shred after first successful unseal.
**Severity:** HIGH

### 2.3 [WARNING] Root Token Used for Ongoing Operations
**File:** Lines 137-139, 147
```sh
ROOT_TOKEN="$(VAULT_TOKEN="$APP_TOKEN" vault token create -policy=loyallia-app -field=token 2>/dev/null || true)"
...
export VAULT_TOKEN="$ROOT_TOKEN"
```
**Finding:** The root token from init.json is used as the ongoing `VAULT_TOKEN`. Root tokens should be **revoked immediately after initialization** and replaced with a time-limited admin token or the app-specific token.

**Recommendation:** After policy creation and app token generation, revoke the root token:
```sh
vault token revoke -self  # Revoke root token after setup
```
**Severity:** HIGH

### 2.4 [WARNING] App Token File Permission 0444 (World-Readable)
**File:** Lines 324-327
```sh
vault token create -policy=loyallia-app -field=token >/vault/runtime/app-token 2>/dev/null || true
chmod 0444 /vault/runtime/app-token 2>/dev/null || true
```
**Finding:** The Vault app token is written to `/vault/runtime/app-token` with **0444 permissions** (world-readable). Any container in the stack can read this token, escalating lateral movement risk.

**Same issue on line 317-319** for other runtime secrets:
```sh
chmod 0444 /vault/runtime/postgres_password /vault/runtime/redis_password ...
```

**Recommendation:** Use 0400 (owner-read only) and ensure the file is owned by the correct service user:
```sh
chmod 0400 /vault/runtime/app-token
chown 1000:1000 /vault/runtime/app-token  # Match the service UID
```
**Severity:** HIGH

### 2.5 [INFO] Rescue Init Injection
**File:** Lines 109-113
```sh
if [ -n "${VAULT_RESCUE_INIT_JSON:-}" ] && [ -f "$VAULT_RESCUE_INIT_JSON" ]; then
    cp "$VAULT_RESCUE_INIT_JSON" /vault/file/init.json
    echo "Injected rescue init.json from $VAULT_RESCUE_INIT_JSON"
fi
```
**Finding:** Rescue init.json injection mechanism exists. This is good for disaster recovery but introduces a supply-chain risk if the rescue file is compromised.
**Severity:** INFO -- Document and secure the rescue procedure

### 2.8 Vault Policy (Inline, Not External)
**File:** Lines 322-323
```sh
printf '%b' "path \"secret/data/loyallia/*\" {\n  capabilities = [\"read\", \"create\", \"update\", \"patch\"]\n}\n" >/vault/runtime/loyallia-app.hcl
vault policy write loyallia-app /vault/runtime/loyallia-app.hcl
```
**Finding:** The Vault policy is defined inline in init.sh, not in a separate `deploy/vault/policies/` directory (the directory doesn't exist). The policy grants **read, create, update, patch** on `secret/data/loyallia/*`.

**Issues:**
- No `delete` capability - good (prevents secret deletion)
- No `list` capability - acceptable
- Has `create`, `update`, `patch` - app can WRITE secrets, not just read. For a Django app, `read` only is recommended. If the app needs to update PlatformSettings to Vault, this is justified but should be scoped.

**Recommendation:** Move policy to a proper HCL file in `deploy/vault/policies/loyallia-app.hcl` for version control. Consider splitting into `loyallia-app-read` and `loyallia-app-write` policies.
**Severity:** MEDIUM

## 3. VAULT CLIENT (backend/common/vault.py)

### 3.1 Secret Retrieval Priority

Priority: Test overrides > Vault KV v2 > env_fallback > default
**Finding:** Well-designed priority chain. Test overrides are highest but are test-only by design. Vault takes precedence over env. `strict=True` mode raises on missing secrets (used in production.py).
**Severity:** NONE -- GOOD

### 3.2 [WARNING] No TLS Certificate Verification
**File:** Lines 102-127 (implicit)
```python
import urllib.request
...
req = urllib.request.Request(url, headers=headers, method="GET")
with urllib.request.urlopen(req, timeout=5) as response:
```
**Finding:** Uses `urllib.request` without a custom SSL context. For self-signed certs (auto-generated by init.sh), this will fail in production unless `PYTHONHTTPSVERIFY=0` is set, which is dangerous. The code does not handle SSL verification errors gracefully.

**Recommendation:** Either:
1. Use properly signed certificates in production (Let's Encrypt or internal CA)
2. Mount the Vault CA cert and configure `ssl.create_default_context(cafile=...)`
3. Add an explicit SSL context parameter to the Vault client
**Severity:** MEDIUM

### 3.3 [WARNING] Default VAULT_SECRET_PATH Points to Development
**File:** Line 20
```python
VAULT_SECRET_PATH = os.environ.get("VAULT_SECRET_PATH", "secret/data/loyallia/development")
```
**Finding:** The default Vault secret path is the **development** path. If `VAULT_SECRET_PATH` is not set in production, the app will silently read development secrets.

However, this risk is **mitigated** by:
- `production.py` calling `enforce_settings_environment(mode="production")` which checks VAULT_SECRET_PATH contains `production`
- `docker-compose.prod.yml` explicitly sets `VAULT_SECRET_PATH: secret/data/loyallia/production`

**Recommendation:** Make the default empty and require explicit configuration, or at minimum add a loud warning log when using the default.
**Severity:** LOW (mitigated)
